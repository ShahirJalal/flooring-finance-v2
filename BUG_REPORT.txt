1. [HIGH] Almost any malformed request returns 500 instead of a proper 4xx
================================================================================
Root cause: backend/src/main/java/com/flooring/finance/exception/
GlobalExceptionHandler.java only has specific handlers for
ResourceNotFoundException, MethodArgumentNotValidException,
IllegalArgumentException and BadCredentialsException. Every other
exception type falls through to the generic catch(Exception) handler,
which reports a generic 500 "Internal Server Error".

Confirmed reproducible for:
  - Malformed JSON body:
      curl -X POST https://finance.experimentbuild.com/api/auth/login \
        -H "Content-Type: application/json" -d '{not json'
      -> 500 (should be 400)

  - Non-numeric path id:
      curl -b cookies.txt https://finance.experimentbuild.com/api/jobs/abc
      -> 500 (should be 400)

  - Invalid enum value for entry category:
      curl -b cookies.txt -X POST https://finance.experimentbuild.com/api/jobs \
        -d '{"name":"x","entries":[{"category":"BOGUS","description":"x","amount":10}]}'
      -> 500 (should be 400)

  - Job name / customerName / entry description longer than the DB column
    (name > 200 chars, customerName > 150 chars, description > 255 chars)
      -> 500 (should be 400, no @Size validation exists on JobRequest/
         JobEntryRequest to catch this before it hits Postgres)

  - Entry amount too large for the numeric(12,2) column
      curl ... -d '{"name":"x","entries":[{"category":"INCOME","description":"x","amount":99999999999999}]}'
      -> 500 (should be 400)

  - Unparseable jobDate (non-ISO format):
      curl ... -d '{"name":"x","jobDate":"14/08/2026","entries":[]}'
      -> 500 (should be 400)

  - Wrong HTTP verb on any route:
      GET  /api/auth/login   -> 500 (should be 405)
      PATCH /api/jobs/1      -> 500 (should be 405)
      GET  /api/jobs/        (trailing slash) -> 500

Impact: bad input is reported to the client as "an unexpected error
occurred" (implying a server bug) instead of a clear validation message,
and every occurrence logs a full stack trace server-side.

Fix: add handlers in GlobalExceptionHandler for
HttpMessageNotReadableException, MethodArgumentTypeMismatchException,
HttpRequestMethodNotSupportedException and DataIntegrityViolationException
(mapping to 400/405 as appropriate), and add @Size/@Digits constraints to
JobRequest / JobEntryRequest matching the entity column limits so bad
input is rejected with 400 before it ever reaches the database.

STATUS: FIXED. All eight repro cases now return the correct status code
against a rebuilt live local build:
  malformed JSON                                -> 400  (fixed)
  non-numeric id                                 -> 400  (fixed)
  invalid enum                                   -> 400  (fixed)
  oversized name (300ch)                         -> 400  (fixed)
  huge amount                                    -> 400  (fixed)
  unparseable date                               -> 400  (fixed)
  wrong verb (GET on /login, PATCH on /jobs/1)   -> 405  (fixed)
  trailing slash (GET /api/jobs/)                -> 404  (fixed, was 500)

The trailing-slash case needed a separate fix from the other seven, as
suspected: it was throwing NoResourceFoundException (Spring 6 turned off
trailing-slash matching by default). Added
@ExceptionHandler(NoResourceFoundException.class) -> 404 in
GlobalExceptionHandler to close it.

Also added log.error(...) to handleGeneric() (the catch-all Exception
handler), so any future gap like this one shows up in the backend logs
instead of leaving zero trace.

================================================================================
2. [MEDIUM] Entry amount precision isn't validated, and the API response
   after create/update doesn't reflect what was actually persisted
================================================================================
JobEntryRequest.amount has @NotNull @Positive but no @Digits constraint,
so values with more than 2 decimal places are accepted, e.g.:

  curl -b cookies.txt -X POST https://finance.experimentbuild.com/api/jobs \
    -d '{"name":"x","entries":[{"category":"INCOME","description":"d","amount":100.999}]}'

Response immediately returns "amount":100.999, "totalIncome":100.999,
"profit":100.999 - but a follow-up GET on the same job shows what
Postgres actually stored: "amount":101.00 (rounded to the numeric(12,2)
column, HALF_UP).

Same underlying issue shows up on PUT: right after updating a job, the
response's "updatedAt" field is stale - identical to "createdAt" - even
though the update succeeded. Only a subsequent GET shows the real,
correct updated timestamp.

Root cause in both cases: the response DTO is built from the in-memory
JPA entity before Hibernate's flush actually applies (rounding via the
column scale, and the @UpdateTimestamp value). If any client trusts the
immediate save response instead of refetching, it will briefly show
wrong numbers/timestamps.

Fix: add @Digits(integer=10, fraction=2) to JobEntryRequest.amount so
out-of-precision input is rejected with 400 instead of silently
truncated later; and either force a flush before building the response
(saveAndFlush / entityManager.flush()) or re-read the persisted values
before mapping to the response DTO.

STATUS: FIXED. @Digits(integer=10, fraction=2) added to
JobEntryRequest.amount (a 3-decimal amount now gets 400, not a rounded
100.999 -> 101.00 surprise later). JobService.create/update switched from
save() to saveAndFlush() so @UpdateTimestamp has actually run before the
response DTO is built. Re-tested: PUT response's updatedAt now matches
the immediate follow-up GET exactly.

================================================================================
3. [LOW-MEDIUM, security] Logout does not invalidate the session server-side
================================================================================
Auth is a stateless JWT with no server-side blacklist/revocation list.
POST /api/auth/logout only clears the browser cookie (Set-Cookie with
Max-Age=0). Verified that reusing the *old* cookie value after logging
out still authenticates successfully:

  1. Login, save cookie A
  2. POST /api/auth/logout using cookie A -> 204
  3. GET /api/auth/me using the SAME old cookie A -> 200 (still works)

Anyone who captured the cookie before logout stays "logged in" against
the API for the full 7-day token lifetime regardless of the user
clicking Logout. Lower practical risk for a single-owner internal tool
behind Cloudflare, but worth knowing since httpOnly cookies can still
leak via e.g. a compromised machine or a proxy log.

Fix (optional, given the single-user scope): track a per-user
"tokens valid after" timestamp (or a short server-side denylist) and
bump it on logout / password change.

STATUS: FIXED. Reusing an old cookie after logout now correctly gets
403 regardless of how old that session was at the moment of logout -
0/10 on the previous failure case across repeated runs. See #4 for the
token_version fix that made this unconditional rather than
timing-dependent.

================================================================================
4. [HIGH, new regression from #3's fix] Logging in right after a logout
   or password change can immediately invalidate the brand-new session
================================================================================
Not part of the original report - found during this retest.

JwtAuthFilter now rejects a token if its `iat` (issued-at) claim is not
strictly after the user's `tokens_valid_after` column. The bug is a
precision mismatch between the two values being compared:
  - JWT `iat` is a standard NumericDate - serialized as whole seconds
    since epoch, so it's always floored down to the start of the second
    the token was issued in.
  - `tokens_valid_after` is `Instant.now()` at logout/password-change
    time - full sub-second precision.

If a new login happens in the same wall-clock second as a preceding
logout or password change for that user, the new token's floored `iat`
can land at or before `tokens_valid_after`'s sub-second value, so
`isAfter()` returns false and the brand-new, correctly-authenticated
session is immediately rejected on its very next request - the user
gets bounced straight back to logged-out with no explanation.

This is not a rare edge case - it's the common case, since a real user
(or the frontend) logging back in right after a password change or
logout very often lands in the same second. Reproduced live:

  1. POST /api/auth/login (correct password)      -> 200
  2. POST /api/auth/logout (using that session)     -> 204
  3. POST /api/auth/login again (correct password)   -> 200
  4. GET /api/auth/me using the session from step 3   -> 403 (should be 200)

Ran steps 1-4 back to back 10 times: 9 out of 10 runs hit the 403.
Waiting ~1-2 seconds between step 3 and step 4 makes it succeed every
time, confirming the second-boundary theory.

Worse, this also hits the password-change flow itself: changing your
password invalidates your OWN current session immediately (by design -
see #3), but the frontend (settings.component.ts) doesn't know that. It
just shows a "Password changed" toast and leaves the dialog closed - the
next click anywhere silently bounces the user to /login via authGuard,
with no message explaining why. I hit this directly while re-testing:
my own attempt to revert the test password back to the original failed
with a silent 403 because I was still on the now-invalidated session,
and I only recovered by logging in again with the new password.

Fix (backend, addresses the root cause): store tokens_valid_after
truncated to whole seconds (Instant.now().truncatedTo(ChronoUnit.SECONDS))
so it's compared at the same granularity as `iat`, and additionally
subtract a small buffer (e.g. 1-2 seconds) before storing it, so a token
issued in the same second as the cutoff - which in real-world timing is
overwhelmingly a fresh, legitimate post-logout login rather than a stale
pre-logout one - isn't caught by the net meant for genuinely old tokens.

Fix (frontend, independent of the backend fix, still worth doing): after
a successful password change, either re-login automatically to get a
fresh cookie, or explicitly redirect to /login with a "please log in
again with your new password" message - don't leave the user sitting on
a session that's already been invalidated server-side.

STATUS: FIXED, via the token_version approach this section itself
recommended - no more clock comparison anywhere in the revocation check.

Backend:
  - New migration V6: drops tokens_valid_after, adds
    token_version INTEGER NOT NULL DEFAULT 0 on app_user.
  - User entity: tokensValidAfter (Instant) replaced with
    tokenVersion (Integer, defaults to 0).
  - JwtService.generateToken(username, tokenVersion) now embeds a
    `tokenVersion` claim in the token at login time; added
    extractTokenVersion(token). extractIssuedAt(token) removed - nothing
    reads `iat` for authorization purposes anymore.
  - AuthController.login() reads the user's current tokenVersion and
    embeds it in the freshly issued token. logout() and
    changePassword() both do `user.setTokenVersion(user.getTokenVersion() + 1)`
    instead of touching a timestamp.
  - JwtAuthFilter.isStillValidForUser() is now a plain integer equality
    check: `jwtService.extractTokenVersion(token) == user.getTokenVersion()`.
    No Instant, no flooring, no buffer, nothing to tune.

Re-tested against a fully rebuilt local stack (docker compose down -v,
then up --build, so V6 ran from an empty schema):

  Original #4 repro (login/logout/login/auth-me back to back 15 times):
      15/15 succeeded.
  Test A - login, wait 3s, logout, reuse the OLD cookie:
      -> 403 (correct - old session killed).
  Test B - login, logout IMMEDIATELY, reuse the OLD cookie, x10 runs:
      -> 403 every time (FIXED - was 9/10 or 10/10 failing across the
      last two passes; the race window is gone, not just narrowed,
      because there's no clock in the comparison to race against).
  Password-change immediate-invalidation, x10 runs (login, change
  password with no delay, reuse the OLD cookie): -> 403 every time.

Frontend: settings.component.ts's changePassword() success handler
still clears local auth state and redirects to /login with a "Password
changed. Please log in again." message, from three passes ago - this
part remains genuinely fixed and unaffected by any of the backend
changes above.

5. [LOW-MEDIUM, security] No rate limiting or lockout on login
================================================================================
8 rapid wrong-password attempts in a row against /api/auth/login all
returned 401 with no throttling, delay, or lockout after N failures.
The endpoint is open to unlimited brute-forcing of the owner password.

Fix: add a simple per-IP/per-username rate limit or exponential backoff
on repeated login failures (e.g. Bucket4j, or a Cloudflare rate-limiting
rule in front of /api/auth/login since Cloudflare is already in the
stack).

STATUS: FIXED. Added LoginRateLimiter - a small in-memory per-username
lockout (5 failed attempts / 15 min window), no new dependency needed
given this runs as a single instance. Re-tested: 6th failed attempt in a
row returns 429, and the correct password is also blocked with 429 while
locked out.

6. [LOW, UX] Clearing the job name in the Edit dialog silently reverts to
   the old name instead of showing a validation error
================================================================================
File: frontend/src/app/features/jobs/job-detail.component.ts, saveJob():

  name: this.jobForm.name?.trim() || this.job()!.name,

If the owner clears the "Job name" field to empty and hits Save, this
silently substitutes the *previous* name back in rather than blocking
the save the way the "add at least one entry" check does
(messageService warning). Not destructive - no data is lost - but it's
inconsistent (one empty-field case warns, the other silently
no-ops) and could mask an accidental edit.

Fix: validate name the same way entries are validated - if blank, show
a warning and refuse to save, rather than falling back silently.

Note: this fallback is intentional and fine in the *create* flow
(job-list.component.ts), where the comment explains the name field
starts pre-filled with "Job N" as a non-scary placeholder. It's only the
edit flow's silent revert that's a problem, since there the "old" value
being restored is real existing data, not a placeholder.

STATUS: FIXED. job-detail.component.ts's saveJob() now warns ("Job name
is required") and refuses to save on a blank name, same pattern as the
entries check, instead of silently restoring the old name. Create flow
left untouched, as noted above. Re-tested in the live UI.
